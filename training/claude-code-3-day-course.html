Module 1.1 · 20 min

>Claude chat vs Claude Code

Same Claude models, very different way of working. In chat, Claude tells you what to do. In Claude Code, Claude does the work on your files and tools — and shows you what it did.

Claude chat (claude.ai, desktop & mobile apps)

"Phone a brilliant expert"

You describe the problem and paste in what's relevant. Claude answers. You copy the answer back into your files, run it, and report what happened.

Claude Code (terminal, VS Code, Desktop "Code" tab, web)

"The expert sits at your computer"

You delegate a goal. Claude reads your files, runs commands, edits what needs changing, checks its own work — and asks your permission for anything you haven't pre-approved.

The agentic loop

When you give Claude Code a task, it works through three phases that blend together — gather context, take action, verify results — repeating until the task is done. A simple question might only need the first phase; a bug fix cycles through all three many times.

What Claude Code can reach when you run claude in a folder

  • Your project: files in that folder and its subfolders (and other folders only with your permission).
  • Your terminal: any command you could run — build tools, git, package managers, scripts.
  • Your git state: current branch, uncommitted changes, recent commits.
  • Your instructions: CLAUDE.md (team or personal) and auto memory Claude keeps for itself.
  • Extensions you add: MCP connectors, skills, subagents, hooks, plugins.

Its built-in tools fall into five families: file operations, search, execution, web and code intelligence — plus tools to delegate to subagents and to ask you questions.

Not just for developers

"Coding" is in the name, but Claude Code helps with anything you can do from a command line: analysing a folder of CSVs, turning meeting notes into action lists, renaming and organising files, building a one-page HTML dashboard, drafting documentation, or researching a question across many files.

Live demo (5 min): open the same small project in claude.ai and in Claude Code. In chat, ask "what does this project do?" — it can't know without you pasting files. In Claude Code, ask the same question and point out the tool calls (Read, Glob/Grep) appearing in the transcript. Then ask Claude Code to "add a README section on how to run it" and show the permission prompt.

Key message: the model is the same family; the harness (tools + context + permissions) is what changes. People who treat Claude Code like chat (asking for snippets to paste) miss most of the value.

Fix: 'claude' is not recognized after installing

First, close and reopen your terminal — PATH changes only apply to new windows. If it still fails, add the install folder (%USERPROFILE%\.local\bin) to your user PATH:

$currentPath = [Environment]::GetEnvironmentVariable('PATH', 'User')
[Environment]::SetEnvironmentVariable('PATH', "$currentPath;$env:USERPROFILE\.local\bin", 'User')

Close PowerShell, open a new window and run claude --version again.

Installation checkpoint

Most common live blockers: (1) wrong shell — CMD vs PowerShell; (2) not opening a new terminal after install (PATH); (3) TLS-inspecting corporate proxy — needs the CA certificate from IT; (4) account without Claude Code access (free plan, or Team/Enterprise seat without the right role).

Permission prompts — your safety valve

When Claude wants to do something that isn't pre-approved, it stops and asks. A typical prompt shows the exact command or file diff and offers options such as:

  • Yes — allow this one action.
  • Yes, and don't ask again — for that command or web domain in this project (saved to .claude/settings.local.json). File edits approved this way last until the session ends.
  • No (or Esc) — decline. Press Tab on Yes/No first to attach a comment telling Claude what to do instead.
Heads-up: you may start in auto mode

From v2.1.283, new terminal and VS Code sessions start in auto mode by default (if your plan, model and organisation allow it): a separate safety classifier reviews actions instead of prompting you, so you'll see far fewer prompts and risky actions get blocked.

For today's labs, switch to Manual mode so you can watch and approve each step: press Shift+Tab until the status line shows ⏸ manual mode on.

The 5-part prompt formula

Short prompts work, but the more precise you are, the fewer corrections you need. The best prompts usually contain:

1 · Goal
What outcome you want, in one sentence.
2 · Context
Where to look: @files, folders, examples to follow.
3 · Constraints
What not to touch; style; tools or libraries to use or avoid.
4 · Verification
How Claude proves it worked: tests, totals, a screenshot.
5 · Output
Where results go and in what format.
Bonus
"Ask me questions first if anything is unclear."

>Context & sessions: Claude's working memory

The context window is everything Claude can "see" right now: instructions, your CLAUDE.md, the conversation, every file it has read and every command output. It fills up fast — and quality drops as it fills. Managing it is the single biggest lever on result quality.

What fills the context
  • System instructions and tool definitions
  • CLAUDE.md files and auto memory
  • Skill descriptions and connector tool names
  • Your messages and Claude's replies
  • Every file read and every command output
What happens when it's full

Claude Code auto-compacts: it clears old tool output first, then summarises the conversation. Your requests and key decisions survive, but detailed instructions from early on can be lost — so put lasting rules in CLAUDE.md, not in chat.

Module 2.3 · 25 min

>Permissions & safety

Claude Code can run commands on your machine. Permissions decide what it may do without asking. You control this with a permission mode (the baseline) plus rules (specific exceptions).

The six permission modes

⏸ manual mode on

Manual (default)

Asks before file edits, most shell commands and network requests. Reads run freely.

Best for: learning, sensitive or unfamiliar work.
⏵⏵ accept edits on

Accept edits

Edits files and runs common file commands (mkdir, mv, cp…) in your folder without asking; other commands still prompt.

Best for: iterating on work you'll review in a diff.
⏸ plan mode on

Plan

Explores and writes a plan but doesn't edit your files until you approve the plan.

Best for: big, multi-file or unclear changes.
⏵⏵ auto mode on

Auto

No routine prompts: a separate classifier model reviews actions and blocks risky ones. The built-in starting mode from v2.1.283.

Best for: long tasks where you trust the direction.
⏵⏵ don't ask on

Don't ask

Anything that would prompt is denied; only pre-approved tools run. Never in the Shift+Tab cycle.

Best for: locked-down scripts and CI.
⏵⏵ bypass permissions on

Bypass permissions

Skips (almost) all checks. Offers no protection against prompt injection or mistakes.

Only in isolated containers/VMs. Never on your work laptop.

Switching modes

Press Shift+Tab during a session. Try it here:

  • At launch: claude --permission-mode plan (values: default/manual, acceptEdits, plan, auto, dontAsk, bypassPermissions).
  • As your default: set "permissions": { "defaultMode": "default" } in ~/.claude/settings.json%USERPROFILE%\.claude\settings.json.
  • VS Code: click the mode indicator under the prompt box (Manual · Edit automatically · Plan · Auto).
  • From a prompt: type /plan fix the auth bug to plan a single task.

Auto mode in one minute

Blocked by default (examples)
  • Downloading and running code (curl … | bash)
  • Sending sensitive data to external endpoints
  • Production deploys, migrations, terraform destroy
  • Force pushes; git reset --hard, git clean -fd
  • Irreversibly deleting files that existed before the session
  • Granting permissions, changing shared infrastructure
  • Printing live credentials into the transcript
Allowed by default (examples)
  • Reading and editing files in your working folder
  • Installing dependencies already declared in your project
  • Read-only web requests
  • Pushing to branches of the repo you're working in
  • Reading .env to call its matching API

Boundaries you state in chat ("don't push", "wait for my review") are respected as block signals — but they can be lost if the conversation is compacted. For a guarantee, write a deny rule. After 3 blocks in a row (or 20 in a session) auto mode pauses and goes back to prompting. Your organisation can switch auto mode off.

Auto mode reduces prompts — it doesn't guarantee safety

Use it for tasks where you trust the general direction, and keep reviewing results. For sensitive work, use Manual or Plan mode.

Plan mode: think first, then act

In plan mode Claude reads files, may run exploratory commands, and writes a plan — your files stay untouched. When the plan is ready you choose:

  • Yes, and use auto mode — approve and let Claude work (reads Yes, auto-accept edits if auto mode isn't available);
  • Yes, manually approve edits — approve but review each edit;
  • No, keep planning — tell Claude what to change.

Press Ctrl+G to edit the plan in your text editor first. In VS Code the plan opens as a Markdown document you can comment on inline.

Permission rules: allow, ask, deny

Rules fine-tune a mode for specific tools. They're evaluated in a fixed order — deny → ask → allow — and the first match wins, whatever the rule's specificity. A deny rule in any settings file can't be overridden by an allow rule elsewhere.

RuleMatches
Bash(npm run test)Exactly that command
Bash(npm run *)npm run build, npm run test --watch, bare npm run — not npm install
Bash(git commit *)Any git commit …
Bash(git push *) (in deny)Blocks commands that start with git push
PowerShell(Get-ChildItem *)Windows PowerShell tool; aliases like ls, dir, gci match too
Read(./.env) · Read(./secrets/**)Reading that file · anything under secrets/
Edit(/docs/**)Edits under the project's docs/ folder
WebFetch(domain:docs.python.org)Web fetches to that host
mcp__github__*Every tool from the github connector
Bash (no brackets)Every Bash command (as a deny: removes the tool entirely)
Gotchas that trip people up
  • Put the * after the subcommand. Bash(git log *) allows only git log; Bash(git *) allows every git command.
  • Spaces matter: Bash(ls *) doesn't match lsof; Bash(ls*) does. Bash(ls:*) is the same as Bash(ls *).
  • Compound commands are split: an allow rule for safe-cmd * doesn't approve safe-cmd && other-cmd. Deny/ask rules apply if any part matches.
  • Bash rules match the text as written — Bash(curl *) doesn't stop /usr/bin/curl or sh -c 'curl …'. For hard boundaries use the sandbox or hooks.
  • Use Edit(…), not Write(…), for path rules — Claude Code only consults Edit and Read path rules.
  • Path anchors: /path is relative to the settings file's project; //path is an absolute path; ~/path is your home folder.
  • CLAUDE.md is not enforcement. "Never read .env" in CLAUDE.md is a request; Read(./.env) in deny is a rule.

Built-in guard rails

  • Working-directory boundary: Claude can only write inside the folder you started it in (and folders you add with /add-dir).
  • Protected paths are never auto-approved (except in bypass mode): .git, .claude, .vscode, .idea, shell profiles like .bashrc/.zshrc, .gitconfig, .npmrc, .mcp.json and similar.
  • Critical paths: rm of your home folder, the drive root or the project folder always needs a human, whatever your rules say.
  • Sandboxing (/sandbox): OS-level file and network isolation for shell commands on macOS, Linux and WSL 2 (not native Windows). Pairs well with Manual mode for fewer prompts.
  • Workspace trust: a folder's own settings, hooks and connectors don't take effect until you trust it.

A sensible starter .claude/settings.json

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(git add *)",
      "Bash(git commit *)",
      "Bash(python -m unittest *)",
      "WebFetch(domain:code.claude.com)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}

The $schema line gives you autocomplete and validation when editing the file in VS Code.

Seven golden rules for safe use
  1. Start in Manual or Plan mode on unfamiliar or sensitive work.
  2. Never use bypass permissions outside an isolated container or VM.
  3. Deny secrets explicitly (Read(./.env)) — instructions alone aren't enough.
  4. Review diffs (/diff) before you commit or share outputs.
  5. Commit often — git is the real undo button.
  6. Treat web pages, documents and third-party connectors as untrusted input (prompt injection is real).
  7. Follow your organisation's data-handling policy — only use data you're allowed to use with AI tools.

>Connectors: plugging Claude Code into your tools (MCP)

The Model Context Protocol (MCP) is an open standard for connecting AI tools to external systems — issue trackers, wikis, databases, design tools, browsers. Each connection is an MCP server; in Claude apps they're often called connectors.

When to add a connector

When you catch yourself copying data into the chat from another tool. Once connected, Claude reads and acts on that system directly: "Add the feature described in JIRA issue ENG-4521 and open a PR", "Update our email template from the new Figma designs posted in Slack".

Two kinds of server

Remote · HTTP

A hosted service at a URL

Notion, Sentry, GitHub, Stripe, HubSpot… Usually you sign in through your browser (OAuth), or pass a token in a header.

claude mcp add --transport http notion https://mcp.notion.com/mcp
Local · stdio

A program on your machine

Started by Claude Code as a subprocess — for things that need local access, like a browser or a database socket. Everything after -- is the command to run.

claude mcp add playwright -- npx -y @playwright/mcp@latest

Three ways connectors reach Claude Code

  1. claude mcp add … in your terminal (works the same in PowerShell, CMD, zsh and bash). Run it outside a Claude session.
  2. A .mcp.json file in the project — shared with the team through git. Teammates get an approval prompt the first time.
  3. claude.ai connectors — added at claude.ai/customize/connectors (on Team/Enterprise, by admins) appear automatically when you sign in to Claude Code with that claude.ai account. They show up in /mcp labelled as coming from claude.ai.

Plugins (later today) can also bundle MCP servers. In VS Code, type /mcp in the chat panel to add, remove, enable and authenticate servers without the terminal.

  3. Use it 
    Use the claude-code-docs server to look up how to pass arguments to a skill
    Approve the first tool call if asked. The tool call is labelled with the server name — proof the answer came from the connector. (Normally you don't need to name the server; naming it just guarantees it's used.)
  4. Manage it inside a session 
    /mcp
    See status, authenticate, enable/disable or reconnect servers.
  5. Remove it when done (optional) 
    claude mcp remove claude-code-docs

Servers that need sign-in

Hosted services such as Sentry, Notion or Linear use OAuth: add the URL, then authenticate.

claude mcp add --transport http sentry https://mcp.sentry.dev/mcp

claude mcp list shows ! Needs authentication — that's expected. Start claude, run /mcp, select the server and choose Authenticate (or run claude mcp login sentry from your shell). Servers that use a static token take it at add time:

claude mcp add --transport http github https://api.githubcopilot.com/mcp/ --header "Authorization: Bearer YOUR_GITHUB_PAT"

Using connectors well

  • Just ask. Claude picks relevant tools itself; name the server when you want to be sure.
  • Reference resources with @: analyse @github:issue://123 and suggest a fix.
  • Server prompts become commands: they appear in the / menu as /mcp__server__prompt.
  • Pre-approve trusted tools with rules like mcp__claude-code-docs__* in your allow list.
  • Context-friendly: tool definitions are loaded on demand (tool search), but each server still adds names and instructions — remove servers you don't use.
Connector security checklist
  • Only connect servers you trust. The Anthropic Directory (claude.ai/directory) lists reviewed connectors, but no MCP server is security-audited by Anthropic.
  • Servers that fetch external content (web pages, emails, tickets) can carry prompt-injection attempts. Keep an eye on what Claude does after reading them.
  • Least privilege: read-only database users, fine-grained tokens scoped to specific repositories.
  • Keep tokens out of git: in .mcp.json use ${API_KEY} environment-variable expansion instead of pasting secrets.
  • Check with your organisation before connecting client systems; admins can allow-list or block servers centrally.
Troubleshooting connectors
  • /mcp says "No MCP servers configured" — you added a local-scope server from a different folder. Re-add it here, or use --scope user.
  • Edited .mcp.json but nothing changed — Claude Code reads it at startup; exit and restart. If you previously rejected it: claude mcp reset-project-choices.
  • Timeout on first start — npx may still be downloading. Raise the limit: MCP_TIMEOUT=60000 claude$env:MCP_TIMEOUT = "60000"; claude.
  • Connected but no tools — usually a missing environment variable (API key). Pass --env KEY=value when adding.
  • "Server already exists" — remove it first (claude mcp remove <name>) or pick another name.
  • A claude.ai connector is missing — run /status: connectors only load when you're signed in with a claude.ai subscription (not an API key or cloud provider).

>Skills: turn repeatable work into your own slash commands

A skill is a folder with a SKILL.md file: a short description (when to use it) plus instructions (what to do). Type /skill-name to run it — or let Claude load it automatically when your request matches the description.

Where skills live

Why skills beat copy-pasted prompts
  • Consistent results — the same checklist every time
  • Shareable — commit to the repo, colleagues get /your-skill
  • Cheap — only the description sits in context until the skill runs

Subagents: helpers with their own context

A subagent works in a separate context window and returns only a summary — great for research that reads many files. Claude Code has built-ins (Explore for fast read-only searching, Plan for planning research, general-purpose for multi-step work) and delegates to them automatically. You can also ask:

Custom subagents are Markdown files in .claude/agents/ (project) or ~/.claude/agents/ (personal). The easiest way to make one is to ask Claude to create it:

---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review code for injection flaws,
auth problems, secrets in code and insecure data handling.
Give specific line references and suggested fixes.

Hooks: guaranteed automation

Hooks run your own command at fixed moments — before or after a tool runs, when Claude needs your input, when a session starts or stops. Unlike instructions, they always fire. Classic uses: auto-format after every edit, block edits to protected files, notify you when Claude is waiting.

Add to %USERPROFILE%\.claude\settings.json — a dialog pops up when Claude needs you:

{
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "powershell.exe -Command \"[System.Reflection.Assembly]::LoadWithPartialName('System.Windows.Forms'); [System.Windows.Forms.MessageBox]::Show('Claude Code needs your attention', 'Claude Code')\""
          }
        ]
      }
    ]
  }
}

Add to ~/.claude/settings.json — a desktop notification appears when Claude needs you:

{
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code needs your attention\" with title \"Claude Code\"'"

      }

  }
}

No notification? Run osascript -e 'display notification "test"' once, then allow notifications for Script Editor in System Settings → Notifications.

Check it with /hooks (read-only browser). If your settings file already has a hooks key, add the event alongside the existing ones. Or simply ask: "write a hook that notifies me when you need input".

Hooks run with your permissions

A hook is a command on your machine. Only add hooks you understand, and review hooks in any repository you clone — a folder's hooks only run after you trust it.

Troubleshooting

Start with claude doctor (shell) or /doctor (in a session). Still stuck? Email your facilitator with a screenshot.

Installation & sign-in

claude isn't found / isn't recognised

Open a new terminal first. Then add the install folder to PATH — Windows: %USERPROFILE%\.local\bin (see the command in Install); macOS: echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc && source ~/.zshrc. If you only installed the VS Code extension, install the CLI too — the extension doesn't add claude to PATH.

Behind a corporate proxy or firewall

Ask IT for the proxy address and set it before installing:

$env:HTTP_PROXY = 'http://proxy.example.com:8080'
$env:HTTPS_PROXY = 'http://proxy.example.com:8080'
irm https://claude.ai/install.ps1 | iex
export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080
curl -fsSL https://claude.ai/install.sh | bash

Test connectivity with curl -sI https://downloads.claude.ai/claude-code-releases/latest (Windows: curl.exe -sI …) — a 200 means you can reach the download server; a 403 usually means a proxy or filter is blocking it. Domains to allow-list: api.anthropic.com, claude.ai, claude.com, platform.claude.com, downloads.claude.ai and (for claude.ai connectors) mcp-proxy.anthropic.com.

TLS errors: unable to get local issuer certificate, SELF_SIGNED_CERT_IN_CHAIN

Your network inspects TLS traffic. Get the corporate CA certificate (a .pem file) from IT. For the install on macOS/Linux: curl --cacert /path/to/corporate-ca.pem -fsSL https://claude.ai/install.sh | bash. On Windows, IT adds the CA to the Windows certificate store. Then point Claude Code at it:

$env:NODE_EXTRA_CA_CERTS = 'C:\path\to\corporate-ca.pem'
export NODE_EXTRA_CA_CERTS=/path/to/corporate-ca.pem
"Claude Code access has not been granted" / 403 after login

Your account doesn't include Claude Code — e.g. the free plan, or a Team/Enterprise seat without a role that includes Claude Code. Ask your admin, or sign in with another account via /login. Run /status to see which account and method are active.

Login fails in WSL, over SSH or in a container

The browser can't reach the local callback. Copy the URL Claude Code prints into a browser on your machine and complete sign-in there; if it asks for a code, paste it back into the terminal.

Windows: "requires either Git for Windows (for bash) or PowerShell"

Neither shell was found. Make sure powershell.exe is on PATH (or install PowerShell 7), or install Git for Windows. If Git is installed but not detected, set CLAUDE_CODE_GIT_BASH_PATH to C:\Program Files\Git\bin\bash.exe in the env block of your settings.json.

Using Claude Code

Too many permission prompts
  • Tick "Yes, and don't ask again" for commands you trust, or add allow rules in /permissions.
  • Run /fewer-permission-prompts to get a suggested allow list from your history.
  • Use Accept-edits mode while iterating, or auto mode for longer tasks you trust.
  • On macOS/Linux/WSL 2, /sandbox lets sandboxed commands run without prompts.
Auto mode keeps blocking something I need

Open /permissions → Recently denied and press r to retry with manual approval, or switch to Manual mode for that step. Name the exact action you approve in your message (e.g. "force-push to my branch feature-x is fine"). Repeated false positives usually mean the classifier lacks context about trusted infrastructure — admins can configure it, and you can report it with /feedback.

Claude ignores my CLAUDE.md
  • Run /context — is the file listed under Memory files? If not, it's in the wrong place.
  • Make instructions concrete ("use 2-space indentation", not "format nicely") and remove contradictions.
  • Trim it — long files dilute important rules. /doctor prompt-audit can review your instruction files.
  • Anything that must always happen belongs in a hook or permission rule.
Claude seems forgetful, slow or confused in a long session

The context is cluttered. Run /context to see why, /compact with a focus, or /clear and restart with a sharper prompt. Put durable instructions in CLAUDE.md, and delegate big investigations to a subagent.

I hit my usage limit

Run /usage to see your limits and what's consuming them. /rate-limit-options shows choices such as waiting for the reset, adding usage credits or upgrading. Long contexts, very high effort and many parallel agents use more.

Something broke after I changed a setting, skill or hook

Start with claude --safe-mode — it disables CLAUDE.md, skills, plugins, hooks and MCP servers so you can tell whether a customisation is the cause. /doctor also flags unparseable settings files and slow hooks.

VS Code: Spark icon missing or Claude never responds

Open a file (the toolbar icon needs one) or use the Status Bar ✻ Claude Code item; check VS Code is 1.94+; run Developer: Reload Window; disable conflicting AI extensions; trust the workspace. If responses never arrive, run claude in a terminal to see a more detailed error.
