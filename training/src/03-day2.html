>The slash commands that matter

Type / to open the command menu, keep typing to filter, press Tab to complete and Enter to run. A command only counts at the start of your message; anything after it becomes its arguments.

Module 2.2 · 10 min

>Context & sessions: Claude's working memory

The context window is everything Claude can "see" right now: instructions, your CLAUDE.md, the conversation, every file it has read and every command output. It fills up fast — and quality drops as it fills. Managing it is the single biggest lever on result quality.

What fills the context
  • System instructions and tool definitions
  • CLAUDE.md files and auto memory
  • Skill descriptions and connector tool names
  • Your messages and Claude's replies
  • Every file read and every command output
What happens when it's full

Claude Code auto-compacts: it clears old tool output first, then summarises the conversation. Your requests and key decisions survive, but detailed instructions from early on can be lost — so put lasting rules in CLAUDE.md, not in chat.

Your context toolkit

ToolUse it to…
/contextSee a breakdown of what's using space, with suggestions
/compact focus on the API changesSummarise now, steering what the summary keeps
/clearStart fresh between unrelated tasks (the old conversation stays in /resume)
/btw …Ask something without adding it to the history
"Use a subagent to investigate…"Research in a separate context; only the summary comes back
Rewind → Summarize from here / up to hereCompress just part of a long conversation

Sessions: pick up where you left off

Every conversation is saved locally (under ~/.claude/projects/%USERPROFILE%\.claude\projects\, kept 30 days by default). Each new session starts with a fresh context; CLAUDE.md and auto memory carry knowledge across sessions.

Checkpoints & rewind

Every prompt you send creates a checkpoint. Press Esc Esc on an empty prompt (or run /rewind), pick a point and choose:

Restore code & conversation
Go back completely.
Restore conversation
Rewind the chat, keep current files.
Restore code
Undo file edits, keep the chat.
Summarize from here
Compress later messages to free space.
Summarize up to here
Compress earlier messages, keep recent ones.
Never mind
Back out without changes.
What rewind can't undo
  • Files changed by shell commands (rm, mv, cp, scripts) — only edits made by Claude's file-editing tools are tracked.
  • Anything in an external system: databases, APIs, emails, deployments, pushed commits.
  • Most edits made by background subagents.

Checkpoints are a seatbelt, not version control. Commit often — git is your real undo.

Three habits of effective users
  1. /clear between unrelated tasks. Kitchen-sink sessions degrade results.
  2. Corrected Claude twice on the same thing? /clear and write a better first prompt using what you learned.
  3. Name sessions like branches (/rename client-deck-data) so multi-day work is easy to resume.

Make context visible (3 min): run /context in a fresh session, have Claude read two or three lab files, run it again, then /compact with a focus and run it a third time. The grid makes the point faster than any slide.

Key message: rules that matter belong in CLAUDE.md, not in chat. They survive compaction and every new session; a correction typed in chat may not.

Watch for: claude -c run from a different folder. It continues the most recent conversation in that folder, so yesterday's session seems lost: cd back to the folder they worked in first.

Module 2.3 · 25 min

>Permissions & safety

Claude Code can run commands on your machine. Permissions decide what it may do without asking. You control this with a permission mode (the baseline) plus rules (specific exceptions).

The six permission modes

⏸ manual mode on

Manual (default)

Asks before file edits, most shell commands and network requests. Reads run freely.

Best for: learning, sensitive or unfamiliar work.
⏵⏵ accept edits on

Accept edits

Edits files and runs common file commands (mkdir, mv, cp…) in your folder without asking; other commands still prompt.

Best for: iterating on work you'll review in a diff.
⏸ plan mode on

Plan

Explores and writes a plan but doesn't edit your files until you approve the plan.

Best for: big, multi-file or unclear changes.
⏵⏵ auto mode on

Auto

No routine prompts: a separate classifier model reviews actions and blocks risky ones. The built-in starting mode from v2.1.283.

Best for: long tasks where you trust the direction.
⏵⏵ don't ask on

Don't ask

Anything that would prompt is denied; only pre-approved tools run. Never in the Shift+Tab cycle.

Best for: locked-down scripts and CI.
⏵⏵ bypass permissions on

Bypass permissions

Skips (almost) all checks. Offers no protection against prompt injection or mistakes.

Only in isolated containers/VMs. Never on your work laptop.

Switching modes

Press Shift+Tab during a session. Try it here:

  • At launch: claude --permission-mode plan (values: default/manual, acceptEdits, plan, auto, dontAsk, bypassPermissions).
  • As your default: set "permissions": { "defaultMode": "default" } in ~/.claude/settings.json%USERPROFILE%\.claude\settings.json.
  • VS Code: click the mode indicator under the prompt box (Manual · Edit automatically · Plan · Auto).
  • From a prompt: type /plan fix the auth bug to plan a single task.

Auto mode in one minute

Blocked by default (examples)
  • Downloading and running code (curl … | bash)
  • Sending sensitive data to external endpoints
  • Production deploys, migrations, terraform destroy
  • Force pushes; git reset --hard, git clean -fd
  • Irreversibly deleting files that existed before the session
  • Granting permissions, changing shared infrastructure
  • Printing live credentials into the transcript
Allowed by default (examples)
  • Reading and editing files in your working folder
  • Installing dependencies already declared in your project
  • Read-only web requests
  • Pushing to branches of the repo you're working in
  • Reading .env to call its matching API

Boundaries you state in chat ("don't push", "wait for my review") are respected as block signals — but they can be lost if the conversation is compacted. For a guarantee, write a deny rule. After 3 blocks in a row (or 20 in a session) auto mode pauses and goes back to prompting. Your organisation can switch auto mode off.

Auto mode reduces prompts — it doesn't guarantee safety

Use it for tasks where you trust the general direction, and keep reviewing results. For sensitive work, use Manual or Plan mode.

Plan mode: think first, then act

In plan mode Claude reads files, may run exploratory commands, and writes a plan — your files stay untouched. When the plan is ready you choose:

  • Yes, and use auto mode — approve and let Claude work (reads Yes, auto-accept edits if auto mode isn't available);
  • Yes, manually approve edits — approve but review each edit;
  • No, keep planning — tell Claude what to change.

Press Ctrl+G to edit the plan in your text editor first. In VS Code the plan opens as a Markdown document you can comment on inline.

Permission rules: allow, ask, deny

Rules fine-tune a mode for specific tools. They're evaluated in a fixed order — deny → ask → allow — and the first match wins, whatever the rule's specificity. A deny rule in any settings file can't be overridden by an allow rule elsewhere.

RuleMatches
Bash(npm run test)Exactly that command
Bash(npm run *)npm run build, npm run test --watch, bare npm run — not npm install
Bash(git commit *)Any git commit …
Bash(git push *) (in deny)Blocks commands that start with git push
PowerShell(Get-ChildItem *)Windows PowerShell tool; aliases like ls, dir, gci match too
Read(./.env) · Read(./secrets/**)Reading that file · anything under secrets/
Edit(/docs/**)Edits under the project's docs/ folder
WebFetch(domain:docs.python.org)Web fetches to that host
mcp__github__*Every tool from the github connector
Bash (no brackets)Every Bash command (as a deny: removes the tool entirely)
Gotchas that trip people up
  • Put the * after the subcommand. Bash(git log *) allows only git log; Bash(git *) allows every git command.
  • Spaces matter: Bash(ls *) doesn't match lsof; Bash(ls*) does. Bash(ls:*) is the same as Bash(ls *).
  • Compound commands are split: an allow rule for safe-cmd * doesn't approve safe-cmd && other-cmd. Deny/ask rules apply if any part matches.
  • Bash rules match the text as written — Bash(curl *) doesn't stop /usr/bin/curl or sh -c 'curl …'. For hard boundaries use the sandbox or hooks.
  • Use Edit(…), not Write(…), for path rules — Claude Code only consults Edit and Read path rules.
  • Path anchors: /path is relative to the settings file's project; //path is an absolute path; ~/path is your home folder.
  • CLAUDE.md is not enforcement. "Never read .env" in CLAUDE.md is a request; Read(./.env) in deny is a rule.

Open /permissions to see every active rule and which file it came from, add or remove rules, manage extra working directories, and review Recently denied actions from auto mode (press r to retry one with manual approval).

Built-in guard rails

  • Working-directory boundary: Claude can only write inside the folder you started it in (and folders you add with /add-dir).
  • Protected paths are never auto-approved (except in bypass mode): .git, .claude, .vscode, .idea, shell profiles like .bashrc/.zshrc, .gitconfig, .npmrc, .mcp.json and similar.
  • Critical paths: rm of your home folder, the drive root or the project folder always needs a human, whatever your rules say.
  • Sandboxing (/sandbox): OS-level file and network isolation for shell commands on macOS, Linux and WSL 2 (not native Windows). Pairs well with Manual mode for fewer prompts.
  • Workspace trust: a folder's own settings, hooks and connectors don't take effect until you trust it.

A sensible starter .claude/settings.json

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(git add *)",
      "Bash(git commit *)",
      "Bash(python -m unittest *)",
      "WebFetch(domain:code.claude.com)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}

The $schema line gives you autocomplete and validation when editing the file in VS Code.

Seven golden rules for safe use
  1. Start in Manual or Plan mode on unfamiliar or sensitive work.
  2. Never use bypass permissions outside an isolated container or VM.
  3. Deny secrets explicitly (Read(./.env)) — instructions alone aren't enough.
  4. Review diffs (/diff) before you commit or share outputs.
  5. Commit often — git is the real undo button.
  6. Treat web pages, documents and third-party connectors as untrusted input (prompt injection is real).
  7. Follow your organisation's data-handling policy — only use data you're allowed to use with AI tools.

>CLAUDE.md & memory

Every session starts with a fresh context. CLAUDE.md is a plain Markdown briefing that Claude reads at the start of every session — your project's conventions, commands and "always/never" rules.

Where CLAUDE.md files live

ScopeLocationUse for
Project (team)./CLAUDE.md or ./.claude/CLAUDE.mdBuild/test commands, conventions, architecture — commit it
Personal, all projects~/.claude/CLAUDE.md%USERPROFILE%\.claude\CLAUDE.mdYour own preferences ("explain changes briefly", "British spelling")
Personal, this project./CLAUDE.local.mdYour sandbox URLs, test data — add to .gitignore
OrganisationManaged policy file deployed by ITCompany-wide standards and compliance rules

Files in parent folders load too, and CLAUDE.md files in subfolders load when Claude works there. All of them are added together (not overridden).

Create one in 30 seconds

/init

Claude analyses the project and writes a starter file (or suggests improvements if one exists). Then refine it with what Claude couldn't discover by itself. Run /memory to open it, and /context to confirm it loaded (listed under Memory files).

What good looks like

✅ Include❌ Leave out
Commands Claude can't guess (how to run tests, build, lint)Anything Claude can work out by reading the files
Conventions that differ from the defaults (date format, spelling, naming)Generic advice like "write clean code"
Where things go ("reports in reports/, never edit data/raw/")File-by-file descriptions of the project
Workflow rules (branch naming, "plan first for multi-file changes")Long tutorials or pasted documentation (link instead)
Gotchas and non-obvious behaviourInformation that changes often
  • Be concrete and verifiable: "Run npm test before committing" beats "test your changes".
  • Keep it under ~200 lines. For each line ask: "would removing this cause mistakes?" If not, cut it.
  • Emphasise sparingly: "IMPORTANT:" on one line works; on twenty lines it means nothing.
  • Split big files: @docs/style.md imports a file; .claude/rules/*.md holds topic rules, optionally scoped to file paths.
  • Treat it like code: when Claude makes the same mistake twice, add a line. Ask Claude: "you keep doing X — add a rule to CLAUDE.md so this stops happening".

Auto memory: notes Claude keeps for itself

As you work, Claude saves useful learnings — your preferences, corrections, project context — to a per-project MEMORY.md index (the first 200 lines / 25 KB load each session). You'll see messages like "Saved 2 memories".

  • Say "remember that the API tests need a local Redis" → saved to auto memory.
  • Say "add this to CLAUDE.md" → written into your project instructions instead.
  • Browse, edit or switch auto memory off in /memory. It's plain Markdown on your machine.
Memory is guidance, not enforcement

Claude tries hard to follow CLAUDE.md, but compliance isn't guaranteed. Anything that must happen (or must never happen) belongs in a permission rule or a hook.

Example CLAUDE.md

# Q3 sales insights (training lab)

## Commands
- Run tests: `python -m unittest -v`
- Don't install new packages without asking first

## Conventions
- Australian English spelling
- Dates as DD Mon YYYY (e.g. 01 Oct 2026); money in AUD with thousands separators
- Write outputs to `reports/`; never modify files in `data/raw/`

## Workflow
- For changes touching more than two files, propose a plan first
- After editing code, run the tests and show me the result
- When compacting, keep the list of files changed and the test command

Critique, don't lecture (5 min): run /init on the lab folder live, then hold the result against the include / leave-out table. Delete one line Claude could have worked out by reading the files, and add one it couldn't have guessed, such as the date format.

Common misconception: CLAUDE.md is a briefing, not documentation. Keep it short. Anything that must always happen belongs in a permission rule or a hook, because memory is guidance, not enforcement.

Module 2.5 · 7 min

>The workflow: explore → plan → build → verify

Letting Claude jump straight to edits can solve the wrong problem. Separate thinking from doing — and always give Claude a way to check its own work.

  1. Explore (plan mode — nothing changes) 
    read @meeting-notes.md and @sales_q3.csv. what would a client exec care about most?
  2. Plan 
    plan a one-page insights summary and a simple dashboard. list the files you'd create and how you'll verify the numbers. don't edit anything yet
    Press Ctrl+G to tweak the plan, then approve.
  3. Build 
    implement the plan. write reports/insights.md and reports/dashboard.html
  4. Verify 
    recompute the regional totals a second way and confirm they match the report. show me the evidence
  5. Commit (if you're using git) 
    commit these changes with a descriptive message
Give Claude a check it can run

A test suite, a build, a script that recomputes totals, a screenshot to compare against — anything that returns pass/fail. Without one, "looks done" is the only signal and you become the verification loop. Ask Claude to show evidence (the command it ran and its output), not just say it worked.

Skip the plan when the change is small and clear: "if you could describe the diff in one sentence, skip the plan."

For bigger pieces of work: let Claude interview you

I want to build [brief description]. Interview me in detail using the AskUserQuestion tool. Ask about implementation, UX, edge cases, concerns and tradeoffs. Don't ask obvious questions — dig into the hard parts. Keep interviewing until we've covered everything, then write a complete spec to SPEC.md.

Then start a fresh session (/clear) to implement the spec with clean context.

Five failure patterns (and their fixes)

PatternFix
Kitchen-sink session — many unrelated tasks in one conversation/clear between tasks
Correcting over and overAfter two failed corrections, /clear and write a better first prompt

Trust-then-verify gap — plausible output, missed edge casesAlways provide verification (tests, totals, screenshots)

Model the habit: before each demo task, ask the room "how will Claude prove this worked?" and put the answer in the prompt. Use plan mode for the explore step, and show Ctrl+G to edit the plan before approving it.

Why copy, not move?

Moves and renames done with shell commands aren't covered by rewind. Copying (or committing to git first) keeps an easy way back.

Part C — wrap up (2 min)

Part A is mandatory: walk the room at the deny-rule step. The usual slip is saving the rule to local instead of project settings; step 2 (checking the rule's source) is there to catch it.

If someone asks how airtight the deny rule is: it covers Claude's file tools, shell commands Claude Code recognises such as cat, head and tail, and redirections. It does not stop a Python script that opens the file itself; that needs the sandbox (macOS, Linux, WSL 2).
